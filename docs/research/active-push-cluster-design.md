# 按「圈子(cluster)」分群实现部分复制 —— 实施设计

> 结论来源：Codex 两轮复核 + 实测复盘(见 `active-push-1b-design.md §7.5`)。
> 核心判断：**不硬改 corrosion 内部**(风险高、逆其全量复制设计)，改用它**自带的 cluster 隔离**——
> 数据在「选发给谁」那步就按圈子排除(`broadcast/mod.rs:853`、`handlers.rs:1126`)，跨圈子**真不传**(非传后再丢)。

## 1. 核心模型：一个数据范围 = 一个圈子

- **圈子内**：corrosion 原生全量复制(组内每个节点都有该范围的全部数据)——不碰任何内部机制。
- **圈子间**：数据零传输(发送端候选过滤直接排除异圈子节点)。
- **划分单位**：按「数据范围」(一类数据/一组表)切圈子；**圈子成员 = 该数据的生产者 ∪ 消费者**。

落到考核的三类数据：

| 圈子 | 数据 | 成员(生产者+消费者) |
|---|---|---|
| C_flight | 飞行状态 | 侦察(产) + 需要航迹的打击/干扰(消费) |
| C_battle | 战场环境/威胁 | 侦察(产) + 打击(规划) + 干扰(避威胁) |
| C_target | 目标 | 侦察(产) + 打击(打) + 干扰(扰) |

> 圈子成员就是"和这份数据有关系的节点",其余节点完全不在这个圈子里、收不到也不存。

## 2. 一个物理节点属于多个圈子 → 跑多个实例

corrosion 一个进程只能属于**一个**圈子(`agent.rs` 单 `cluster_id` + 单 `db.path`)。
所以一个物理平台若同时和多类数据有关系，就**为每个圈子各跑一个 corrosion 实例**(独立端口/库/bootstrap)：

```
侦察平台(传感器，产出全部三类) → 跑 C_flight + C_battle + C_target 三个实例
打击平台(需战场环境+目标)        → 跑 C_battle + C_target 两个实例
干扰平台(需目标)                 → 跑 C_target 一个实例
```

每平台实例数 = 它涉及的数据类数(本例 ≤3)，部署可控。

## 3. 跨圈子查询网关(对接 4.4.2 任意节点查任意数据)

圈子隔离后，本地只有本圈子的数据。考核 4.4.2 要"任意节点查任意数据"，所以加一层**查询网关**：

- 本平台进程**本地能答的**(属于它所在圈子的数据) → 直接本地 SQL 查(corrosion 本地读，快)。
- **本地没有的**(别的圈子的数据) → 网关**转发到该数据所在圈子的某个节点**，取回结果。
- 优化：网关缓存热点跨圈子结果；维护"哪类数据在哪个圈子"的路由表(静态即可)。

> corrosion 的订阅(subscriptions)是**本地**变化流，不能当远程按需拉取用(Codex 已确认)，
> 所以跨圈子查询必须自己做网关，不能指望它。

## 4. 降量从哪来 —— 以及诚实的局限

**降量来源**：广播式基线把**每类数据复制到全部 100 个节点**；圈子模型只复制到**该圈子成员**。
省下的 = 「不在该圈子的节点 × 该类数据量」。

**最大的降量来自高频、窄需求的数据**：
- 平台**自身遥测/飞行状态**(每个节点持续上报位置)在全量复制下是 100×100 的洪水；
  圈子模型下只发给真正需要它的少数节点 → **省得最多**。这是 30% 的主力。

**诚实的局限(表级圈子的天花板)**：
- 若某类数据**几乎所有角色都要**(如"目标"侦察产、打击+干扰都要 → 圈子≈全员)，
  表级分圈子**省不动**这类数据。
- 要再省，得做**行级**(某条目标只给被指派打它的那个平台) —— 那是更细的划分，
  本方案不做，留作后续(行级触及 corrosion 版本/记账语义，是更大的工程)。

→ **30% 能不能达成 = 取决于数据按"窄需求"可分的程度 + 各类数据的量级分布**。
遥测类数据量大且窄需求时，30% 可达且有余量；若数据全是"全员都要"型，则圈子方案也省不动(那时任何方案都难)。

## 5. 怎么测 30%(对接第三方测评口径)

- **广播式模型(基线)**：所有节点同属**一个** cluster，全量复制三类数据。测全局总传输。
- **智能模型**：按 §1 分三圈子部署，每平台跑对应实例。测全局总传输。
- harness 升级：`run.py`/`sweep.py` 支持「单圈子全量」vs「多圈子分群」两种部署，
  各节点按角色 assign cluster_id + 起对应实例；统计两种部署的全局 `broadcast.sent.bytes + sync.chunk.sent.bytes`。
- 验收：智能模型全局总量 ≤ 广播式 × 70%，且跨圈子查询能查到(功能正确)。

## 6. 实施分步

1. **harness 多圈子编排**：让每个角色节点按数据需求起 1~N 个 corrosion 实例(不同 cluster_id/端口/库)，
   配好同圈子 bootstrap。先验证「圈子间数据零传输、圈子内正常收敛」。
2. **量降量**：跑 广播式(单圈子) vs 智能(多圈子) 对照，重复取均值(杜绝单次结论)，看降幅。
   重点把**遥测类高频数据**纳入负载，体现窄需求数据的省量。
3. **查询网关原型**：一个简单转发层——本地查不到的表 → 按路由表转发到对应圈子节点。
   先打通功能(能跨圈子查到)，再压 QPS(4.4.2)。
4. **控制面隔离**(可选优化)：把不同圈子的 gossip 网络/bootstrap 物理分开，消掉跨圈子的心跳流量。

## 7. 风险与开放问题

- **多实例运维成本**：一个物理节点多实例(多端口/库/进程)，半实物环境要确认可接受。
- **节点动态加入/换组**：平台任务变了要加入新圈子 = 起新实例 + 该圈子内同步历史数据(组内全量，正常)。
- **跨圈子查询是新代码**：网关的可用性/一致性/QPS 是 4.4.2 的关键，需单独设计与压测。
- **表级天花板**：广泛需求的数据省不动(见 §4)，若考核负载以这类为主，需提前评估并考虑行级(更大工程)。
- **和现有 interest/scored_reduce 的关系**：那套保留作**单圈子内**的实验/指标工具(它降的是组内冗余)，
  与圈子分群正交，可叠加但非必须。
