# 任务感知主动推送：改造方案与实验设计

## 0. 对接项目考核指标（北极星）

| 项目要求 | 已建组件 | 差距 |
|---|---|---|
| 4.4.3 **全局数据传输总量降 30%**（智能 vs 广播） | `Random`=广播基线 / `ScoredReduce`=智能减量(含 ring0 flood 接入 selector)；harness mission 拓扑 + `sweep.py` 重复取均值测全局总量 | **1a 推送减量机制已实现但单独不达标**：均值实测无单调趋势、误差带 [-44%,+43%]、30 节点净增 20%(被 anti-entropy 兜底+重传放大吃掉)。**1b(对账按 interest 过滤)是必需项** |
| 4.3.3 GNN+DRL 学**适配度评分函数** | selector `score()`(链路+相关度,手调线性)；`Rl` 分支占位 | 须把 score 换成 GNN+DRL 学习的函数 |
| 4.2.3 任务→数据需求模版 + 多跳路由(gossip) | `interest_routing`(表→关心addr)雏形；SWIM+anti-entropy 多跳/容断 | 须建 侦察/打击/干扰 → 飞行状态/战场环境/目标 的真模版 |
| 4.4.2 1M QPS / 100 节点 / 500Kbps | corrosion SQL 查询层 | 读吞吐扩展，另立工作线（与推送不同轴） |

⚠ **关键张力**：4.4.3 要降量，但 corrosion 全量复制 + anti-entropy 会把数据同步到所有节点，
抵消降量。要真降 30%，需让推送+对账都「按任务需求分发」，配合查询路由（4.4.2 查得到≠每节点都存）。

**最近一步（直指 4.4.3）**：实现 scored 的减量变体（任务无关平台不走快速推送）+ 用 harness
跑「广播 vs 智能」的全局传输总量对照，逼近 30%。

### 0.1 官方考核原文与第三方测评方式（以此为准）

> **4.2.3 基于任务关联分析的智能数据主动推送技术**：建立侦察、打击、干扰等不同任务与作战数据需求的映射关系模型，形成任务关联的数据需求模版；基于「深度图强化学习的态势数据智能推送」关键技术，实现推送数据与作战平台的精准匹配；开展不确定链路通断下数据推送**多跳路由机制(gossip)**研究；研发面向侦察/打击/干扰任务的智能数据主动推送模型，形成技术研究报告。
>
> **4.3.3 基于深度图强化学习的态势数据智能推送技术**：建立态势数据与作战平台的多维特征关系表征模型，用**图神经网络与深度强化学习**算法挖掘态势数据与作战平台间的**适配度评分函数**；在作战时效性与战术规则约束条件下，智能决策出推送的目标平台、内容及路径，减少跨平台传递的通信冗余与传输开销。
>
> **4.4.2 全局并发跨平台查询吞吐 ≥ 100 万 QPS**：支持侦察/打击/干扰 3 类异构无人节点跨平台查询，支持态势感知/决策规划/战损评估 3 类业务流程数据查询。*考核方式（第三方测评）*：半实物环境，构建 **100 节点全链路联通、节点间带宽 500 Kbps**，查询覆盖 3 类节点 + 3 类业务流程，检查全局每秒成功处理查询数 ≥ 100 万 QPS。
>
> **4.4.3 全局数据传输总量降低 30%**：支持挖掘内容含飞行状态/战场环境/目标等数据，构建侦察/打击/干扰任务的数据需求模版，支持 ≥3 类任务的智能主动推送。*考核方式（第三方测评）*：半实物环境，构建执行侦察/打击/干扰 3 类异构无人节点；模型输入含**飞行状态/战场环境/目标**等数据；**分别统计「智能主动推送模型」与「广播式推送模型」的全局数据传输总量，检查智能模型的全局总量降低 30%**。

**测评口径对实现的硬约束**：
- 4.4.3 是 **A/B 对照**：`Random` 策略 = 「广播式推送模型」基线，`ScoredReduce` = 「智能推送模型」；harness 须**分别统计两者全局总传输量**并算降幅，逼近 30%。
- 数据类型固定为 **飞行状态 / 战场环境 / 目标** → 落为表/topic；节点按任务(侦察/打击/干扰)持有 interest profile。
- 测评规模为 **100 节点 / 500 Kbps / 半实物**，harness 终态须能逼近此拓扑（含带宽约束注入）。

## 1. 一句话

把 Corrosion 广播传播时的**随机选 peer** 换成**按价值打分选 Top-K**，再进阶到图强化学习决策，
对比随机基线证明送达率/延迟/带宽的改善。

## 2. 精确改造点

`crates/corro-agent/src/broadcast/mod.rs`（约 700–730 行，`run_transmissions` 内）：

```rust
let broadcast_to = {
    agent.members().read().states.iter()
        .filter_map(|(member_id, state)| {
            // 排除自己 / 异 cluster / ring0(本地广播时) / 已发过的
            if *member_id == actor_id || state.cluster_id != agent.cluster_id()
                || (pending.is_local && ring0.contains(&state.addr))
                || pending.sent_to.contains(&state.addr) { None }
            else { Some(state.addr) }
        })
        .choose_multiple(&mut rng, choose_count)   // ★★ 随机选 K 个 —— 改这里
};
```

候选已由 `filter_map` 筛好；`choose_multiple(rng, K)` 是纯随机。**研究即替换这一步**。

## 3. 现有可复用信号

- **链路质量（RTT）**：`Transport::new(&config.gossip, tx_rtt)` 已采集 RTT；可经 agent 暴露给打分。
- **节点角色/分层**：已有 `ring0`（优先核心成员）二层概念（`members.ring0()`）——把它细化成连续分值。
- **成员状态**：`members().read().states` 含 addr、cluster_id、活跃度等。
- **订阅/关注**：Corrosion 有 subscription（`subs`）机制，可推导"哪个 peer 关心哪些表/数据" → 数据相关度。
- **指标**：已有 `corro.gossip.*` / `corro.broadcast.spawn` 等 metric，实验直接采。

## 4. 实施分阶段

### 阶段 0：插桩抽象（不改行为）
把选 peer 抽成一个可替换函数 + 配置开关，便于 A/B：
```rust
trait BroadcastSelector {
    fn select(&self, candidates: &[MemberRef], payload: &Payload, k: usize) -> Vec<SocketAddr>;
}
// RandomSelector（=现状基线）  /  ScoredSelector  /  RlSelector
```
配置 `gossip.broadcast_strategy = "random" | "scored" | "rl"`，运行时切换跑对照。

### 阶段 1：打分式（Scored）
```
score(peer) = w1·数据相关度(订阅/分片重叠)
            + w2·链路质量(RTT 反向归一)
            + w3·节点角色(ring0/任务角色)
            + w4·(1 − 负载)
→ 选 score 最高的 K 个（可留少量随机名额防"饿死"边缘节点）
```
权重先手调，记录每项贡献，做消融。

### 阶段 2：任务感知（Mission-aware）
引入任务/本体语义：mutation 带 topic/tag，peer 带 interest profile，
数据相关度 = similarity(mutation.topic, peer.interest)。对应文档里的 interest-based dissemination。

### 阶段 3：图强化学习（GraphRL）
网络建图 G=(V,E)，状态=链路/负载/邻居/任务，动作=发给谁/发多少，
奖励=送达率↑、延迟↓、带宽↓。学习传播策略，替换打分函数。

## 5. 对照实验设计

| 维度 | 设置 |
|---|---|
| 基线 | Corrosion 原版（random + ring0） |
| 对照组 | scored / mission-aware / RL |
| 规模 | 多节点集群（用 `corro-devcluster` 起，或容器/虚拟网络）；逐步加到 50–100 节点 |
| 负载 | 注入 SQL 写（不同 topic / 热点分布），可模拟丢包/分区/动态拓扑 |
| 指标 | ① 收敛延迟（写入到全集群可见）② 送达率 ③ 广播总字节/冗余度 ④ 每节点负载 |
| 采集 | 复用 `corro.gossip.*` / `corro.broadcast.*` metric + 自加埋点 |

预期结论：相同收敛目标下，主动推送把无关传播砍掉 → 带宽↓且热点数据延迟↓。

### 5.1 指标参考（按轴，对接 4.4.3 降量）

全局传输总量分**两条轴**，降 30% 必须两轴都看（见 §0 关键张力）。指标名取自代码（`grep corro.broadcast / corro.sync / corro.gossip`），harness 经各节点 Prometheus（端口 9400+i）抓取后求差求和。

**推送轴（broadcast，主动推送直接影响）**

| 指标 | 含义 | 降量看点 |
|---|---|---|
| `corro.broadcast.spawn` | 本节点发起的广播传输**次数** | ★主代理：减量变体应让它随无关 peer 被剔除而下降 |
| `corro.broadcast.recv.count` | 收到的广播条数 | 全集群求和≈总投递量 |
| `corro.broadcast.duplicate.count` | 收到的**重复**广播 | 冗余度，越小越好 |
| `corro.broadcast.dropped` | 被丢弃的广播 | 过载/容量信号 |
| `corro.broadcast.rate_limited` | 被限流的广播 | 配额耗尽信号 |

⚠ **缺口**：上述均为**次数**，无现成的广播**字节**指标。30% 要按字节算，1a 需新增一个 broadcast 发送字节计数器（或用 `spawn × payload_len` 近似）。

**对账轴（sync / anti-entropy，降量的真凶，1b 处理）**

| 指标 | 含义 | 降量看点 |
|---|---|---|
| `corro.sync.chunk.sent.bytes` / `corro.sync.chunk.recv.bytes` | 对账收/发**字节** | ★全局总量的大头，按表过滤 need 后应下降 |
| `corro.sync.changes.sent` / `corro.sync.changes.recv` | 对账收/发的**变更条数** | 与字节互证 |
| `corro.sync.client.needed.v2` | 本节点判定"还缺多少版本" | interest 过滤后应缩小 |
| `corro.sync.requests.recv` | 收到的对账请求数 | 对账频率 |

**收敛 / 上下文**

| 指标 | 含义 |
|---|---|
| 收敛延迟（s） | 外部轮询：写入到全集群（或相关节点）可见的耗时 |
| `corro.gossip.cluster_size` / `corro.gossip.members` | 集群规模，归一化用 |

**全局传输总量** ≈ 推送字节 + 对账字节。降量目标 = 在相同收敛目标下，`scored_reduce`（含 1b）相对 `random` 把该总量压低 ≥30%。

## 6. 风险与注意

- **公平性/活性**：纯 Top-K 可能饿死低分边缘节点 → 保留随机探索名额 + 配合 anti-entropy 兜底（Corrosion 的 sync 仍保证最终收敛）。
- **正确性不变**：只改"发给谁"，不改 CRDT 合并与对账 → 最终一致性不受影响，主动推送只优化"多快、多省"。
- **信号获取成本**：RTT/订阅已有；负载/任务语义需新增采集，注意别让打分本身成为开销瓶颈。
- **实验可复现**：固定随机种子、记录拓扑与负载脚本。

## 8. 1b 设计前提：数据摆放是「降量(4.4.3)」与「1M QPS(4.4.2)」的共同支点

> **详细设计见 [`active-push-1b-design.md`](active-push-1b-design.md)**（数据流/记账状态机/协议改动/正确性/最小切片）。本节只立前提。

1a 实测证明：**只动推送轴治标不治本**——省下的被 anti-entropy 全量兜底 + 重传/rebroadcast
放大吃掉，规模越大越反噬（30 节点净增 20%，见 harness README）。全局传输量主要活在**对账轴**。
但 1b（对账按 interest 过滤）会把 Corrosion 从「全量复制」推向「部分副本」，与 4.4.2 直接耦合，
必须协同设计。

### 8.1 模型转变与内在张力

| | 全量复制（现状） | 部分副本（1b 后） |
|---|---|---|
| 谁存什么 | 每节点存全部表 | 节点只存/同步**其任务关心的表** |
| 查询 | 永远本地读（快，QPS 易达） | 本地没有的 → **路由到持有节点**（多一跳，热点风险） |
| 传输量 | 大（每条数据到每个节点） | 小（跳过不关心的节点）→ 降量来源 |

⚠ **张力**：naive「只存任务数据 + 啥都路由」会砸 4.4.2 的 1M QPS（网络跳 + 持有节点瓶颈）。
全量复制之所以 QPS 友好，正因为读全本地——这是 Corrosion 的强项，1b 不能无脑丢掉。

### 8.2 调和原理：摆放跟着访问模式走，降量才「不花 QPS 成本」

**核心洞察：从某节点删掉的数据，应恰是该节点几乎不查的数据。**

placement 按任务划分 ⇒ 访问模式也按任务划分：侦察节点主查飞行状态、打击主查战场环境+目标、
干扰主查目标——**都本地有、都快**。砍掉的传输（如 战场环境→侦察节点）= 该节点本就不查的数据
⇒ 降量几乎不损本地 QPS；真正要路由的只是少数**跨任务**查询。

→ 多数查询仍本地读 ⇒ 1M QPS 可达；路由的是少数派。**4.4.2 与 4.4.3 共用同一套摆放策略。**

### 8.3 设计约束（1b 必须满足）

1. **placement 从查询访问模式推导**，而非随意配；`interest_routing`/任务模版应反映「谁高频查什么」。
   降量只在「本地不查的数据」上是免费的。
2. **共享/热数据多存几份**：目标(target) 打击+干扰都要 → 都本地存，这类查询不路由。
3. **跨任务查询要有出路**：查询路由 + 路由结果缓存 + 本地存「谁有该数据」的索引/摘要（一跳直达）。
   否则侦察节点查战场环境直接查不到——降量达标但功能不可用。
4. **正确性边界**：CRDT 合并语义不变；变的是「need 哪些版本」。须解决 **版本(事务)→表 映射**
   （一个版本可能跨多表，按表过滤 need 不是干净的版本级操作）。
5. **抑制 1a 暴露的放大**：reduce 下收敛判定与 `max_transmissions` 重审，避免「少直推→多重传」抵消降量。

### 8.4 第三方测评风险

考核查询「应覆盖 3 类节点 + 3 类业务流程」。若测评故意**大量打跨任务查询**，路由比例升高、
持有节点成瓶颈 → QPS 掉。对策见 8.3.2/8.3.3（共享数据多副本 + 缓存 + 索引）。摆放策略须按
**最坏跨任务查询比例**做压力测试，不能只测 mission-aligned 的理想负载。
